# 采集成功率优化 — HTML 内容有效性验证

> 创建时间：2026-03-28
> 管线：superpower-chain Pipeline B
> 状态：收集中

## 原始需求

wf 命令经常采集报错或采集不到内容。核心问题：fetch 拿到 HTML 后缺乏统一的内容有效性验证，导致空内容、反爬页面、登录墙等无效内容不会触发 fallback 到下一层 fetcher。

## 现状分析

### 当前 fetch 链路
```
fetch_html_with_retry() [core.py:1255]
  ├─ urllib (4次重试) → CDP fallback → Selenium fallback → Manual Chrome
  └─ 错误分类器：只处理 HTTP 错误/SSL 错误/网络错误
```

### 现有验证机制（分散且不统一）
| 机制 | 位置 | 触发时机 | 覆盖范围 |
|------|------|----------|---------|
| AntiBotDetectedError | templates.py:67 | WeChat 解析时 | 仅 WeChat |
| V2 quality_low | engine_v2.py:120 | 解析竞赛后 | 仅 V2 引擎 |
| _is_spa_shell() | engine_v2.py:15 | quality_low 后 | 仅 V2 引擎 |

### 关键缺口
1. **fetch 和 parse 之间没有通用验证层** — urllib 返回 200 但内容为空/反爬，直接进入解析
2. **非 WeChat 站点无反爬检测** — 通用站点的反爬页面无人识别
3. **V1 引擎无质量检查** — legacy 解析器对空内容无感知
4. **XiaoHongShu 解析器无验证** — 完全没有内容检查

## 细化记录（B1）

### 技术补充

#### 需求 1: 统一 HTML 内容验证函数

**函数签名**: `validate_fetched_html(html: str, url: str) -> tuple[bool, str]`
- 返回 `(is_valid, reason)`
- **检测项**:
  - 空内容: `html` 为空或仅含空白
  - 过短内容: `<body>` 内文本 < 200 字符（排除 script/style 标签）
  - 反爬/拦截特征词: "验证码"、"环境异常"、"访问频繁"、"请在微信客户端打开"、"Access Denied"、"403 Forbidden"、"Please verify"、"captcha"、"robot"、"blocked"
  - 登录墙: "请登录"、"login required"、"sign in to continue"
  - SPA 空壳: body 文本极少 + script 占比 > 30%（复用 _is_spa_shell 逻辑）
- **插入点**: core.py 约 Line 5005，在 `fetch_html_with_retry` 返回后、parser 选择前

#### 需求 2: 验证失败触发 fallback

**改动方式**: 在 `fetch_html_with_retry()` 返回前增加验证调用
- urllib 返回 HTML → validate → 失败 → 走 CDP fallback（复用现有 `_try_cdp_fallback_after_urllib_failure`）
- CDP 返回 HTML → validate → 失败 → 走 Selenium fallback
- Selenium 返回 HTML → validate → 失败 → 走 Manual Chrome
- 所有 fetcher 都验证失败 → 返回最后一次的 HTML（降级输出，但记录警告）
- **关键**: 验证在 `fetch_html_with_retry` 内部完成，对上层调用者透明

#### 需求 3: 通用反爬/拦截页面检测

**扩展现有机制**:
- 将 `_detect_wechat_antibot()` 的模式泛化为 `_detect_antibot_page(html, url)`
- 添加通用反爬特征: HTTP 状态码嵌入页面 (403/429/503)、Cloudflare/hCaptcha 标志、空 body + 大量 JS
- 保留 WeChat 特有检测作为子集
- 位置: 可放在 core.py 或新建 validation 模块

#### 需求 4: 最终失败原因报告

**改动方式**:
- 在 FetchMetrics 中增加 `validation_failures: list[str]` 字段
- 每次验证失败时记录 `(fetcher_name, reason)`
- 最终输出到 markdown 的 fetch 报告区域
- 日志输出: `WARNING: 所有采集方法均未获取有效内容: [原因列表]`

#### 需求 5: 失败日志持久化

**设计思路**:
- 日志文件位置: `~/.wf/fetch_failures.jsonl`（JSONL 格式，每行一条记录，方便 grep/jq 分析）
- **记录触发条件**:
  - 所有 fetcher 都失败（网络错误、超时等）
  - 所有 fetcher 都通过但内容验证不通过（空内容、反爬、登录墙）
  - 解析阶段失败（HTML 正常但解析出空内容）
- **记录字段**:
  ```json
  {
    "ts": "2026-03-28T14:30:00",
    "url": "https://example.com/page",
    "input_url": "https://example.com/page",
    "fetchers_tried": ["urllib", "cdp", "selenium"],
    "failure_type": "content_invalid|fetch_error|parse_error",
    "failure_reason": "antibot_detected|empty_content|too_short|login_wall|...",
    "last_error": "HTTPError 403",
    "html_size": 1234,
    "validation_details": ["urllib: empty_content", "cdp: antibot_detected"],
    "fetch_mode": "auto",
    "duration_seconds": 12.5
  }
  ```
- **日志管理**: 文件超过 10MB 时自动轮转（重命名为 `.1` 后新建）
- **wf 作为系统命令使用时同样生效** — 日志路径用 `~/.wf/` 而非项目目录，确保 pipx 安装后全局可用
- **后续可基于此日志**: 分析高频失败站点 → 添加路由规则/站点模板 → 持续提升成功率

**结论**：全部通过，无 🔴。以下关键改进纳入设计：

### 评审改进决议

1. **验证放在 fetch_html_with_retry 内部**（方案A）— 对上层透明，复用 fallback 链
2. **双条件判定**：特征词匹配 + body 文本过短，避免误报长文章
3. **阈值分级**：< 50 字符确定无效，50-500 可疑需组合判断
4. **特征词搜索范围限定**：仅搜 `<title>` + `<body>` 前 2000 字符，排除正文区域
5. **新增 fallback 函数**：`_try_fallback_for_invalid_content()`，与现有异常 fallback 分离
6. **总超时保护**：fetch_html_with_retry 增加 120s hard deadline
7. **验证函数自保护**：整体 try/except，异常时放行不阻断
8. **WeChat 检测保留**：通用检测包裹 WeChat 专有检测，`_detect_antibot_page(html, url)` 内部分发
9. **补充反爬特征**：Cloudflare/hCaptcha/腾讯WAF/Akamai 等 CDN/WAF 指纹
10. **日志保留 3 个历史文件**：总上限 40MB
11. **日志写入 try/except 保护**：失败时静默降级
12. **补充字段**：`wf_version`、`hostname`

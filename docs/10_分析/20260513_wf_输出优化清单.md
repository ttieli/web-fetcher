# wf CLI 输出优化清单（来自 AI agent 使用反馈）

> 创建时间：2026-05-13 15:45
> 来源：实际 AI agent 使用 wf 过程中扫到的痛点
> 状态：待 chain 立项实施（A 类 P1，B 类 P0）
> 接收方：本项目（Web_Fetcher / wf）

## 背景

用户扫了一遍 wf 当前输出，整理给"wf 项目组"的优化清单。两条路线：

- **上游**（本清单）：把 `--help` 和报错先优化一轮
- **下游**：wf 优化落地后再写 skill，skill 能薄薄一层只管"触发 + 模式决策"，细节让 AI 自己 `wf --help` 查或看报错 `建议:` 字段路由

## A 类 · --help 可优化点

### A1 · 干掉启动横幅噪音（最值钱）

**现状**：每次跑 wf 都先打印 4 行到 stderr：
```
CDP fetcher available
Loaded configuration from: /Users/tieli/.config/webfetcher/routing.yaml
Compiled 13 routing rules
Config-driven routing system initialized
```

**问题**：
- 污染 `--stdout` 输出（虽然 stderr 不进 stdout，但 AI agent 调用时往往一起捕获）
- 污染 `--help` 输出
- AI 还得过滤这些行

**建议**：默认静默，`-v/--verbose` 时才显示。

**影响位置**：`src/webfetcher/core.py` / `src/webfetcher/cli.py` / `src/webfetcher/routing/config_loader.py` 中的 module-level `logger.info(...)` 启动日志。

### A2 · 加「AI agent 场景速查」段

**建议**：`--help` 按场景列命令，比按参数堆更友好：

```
AI agent 常用场景：

  用户粘贴含 URL 的混合文本    wf "<原文>" --stdout       # 自动 URL 提取
  读文章正文（最常用）          wf URL --stdout --lite
  存网页含图                   wf URL -o ./out/
  静态站快速模式               wf fast URL --stdout
  批量抓取                     wf batch urls.txt -o ./out/
```

### A3 · 陷阱段显式标注

**建议**：`--help` 末尾加"陷阱与限制"段，避开常见误用：

- `--lite` + 想存图片 = **冲突**（lite 模式拦截图片资源）
- 微信/小红书走 CDP 是**路由表自动**（用户不需手动加 `--cdp`）
- 登录态需求 → 需要 `manual_chrome` 模式 + 本机 Chrome 已登录
- `--stdout` + `batch` = 拒绝（batch 模式不支持 stdout）

## B 类 · 错误输出结构化（P0，大头）

### B1 · 结构化错误对象替代 Python traceback

**现状**：`wf not-a-url` 直接抛 traceback：

```
Traceback (most recent call last):
  File "/.../core.py", line 609, ...
  raise ValueError(f"URL missing scheme: {url}")
ValueError: URL missing scheme: not-a-url
During handling of the above exception, another exception occurred:
Traceback ...
```

AI 看到 traceback 会**误判成 bug**。

**建议**：结构化错误（exit 非 0，stderr）：

```
错误类型: URL_INVALID
说明: URL 缺少 scheme (http:// 或 https://)
建议: 试试 wf https://example.com
```

### B2 · 错误分类至少覆盖 8 种

| 类型 | 触发场景 | 建议 |
|------|---------|------|
| `URL_INVALID` | URL 格式错（缺 scheme、特殊字符等）| 给一个正确的示例 |
| `DNS_FAILURE` | 域名解析失败 | 检查网络/拼写 |
| `SSL_ERROR` | SSL 握手失败 / 证书问题 | 加 `--insecure`（如该参数存在） |
| `HTTP_4XX` | 4xx 客户端错误 | 区分 403（反爬→换 fetcher）vs 404（URL 错）|
| `HTTP_5XX` | 5xx 服务端错误 | 稍后重试 |
| `TIMEOUT` | 超时 | 增大 `--timeout` |
| `CDP_LAUNCH_FAILED` | headless Chrome 启动失败 | 检查 Chrome 装否、端口冲突 |
| `CONFIG_ERROR` | routing.yaml / template.yaml 解析失败 | 指明文件 + 行号 |

### B3 · "Error classified as unknown" 改人类可读

**现状**：日志里出现 `Error classified as unknown` 是给开发者看的内部分类失败提示。

**建议**：分类失败时改成：
```
未知错误（错误分类器未识别）
原始: <原始 error message>
建议: 把这个错误反馈给 wf 项目组
```

### B4 · 重试终结时打一句总结

**现状**：重试 3 次失败后，日志只有 3 段重试过程，没有最终总结。AI 在长日志里找不到结论。

**建议**：失败终结时输出一行：
```
重试 3 次仍失败，最终错误: SSL_ERROR — 证书已过期 (cert.notAfter < now)
```

### B5 · traceback 仅 `--debug` 时显示

**现状**：所有 exception 都 print traceback。

**建议**：默认隐藏 traceback，只输出 B1 的结构化错误。`--debug` 才打 traceback。

## 实施建议

### 优先级

| 优先级 | 内容 | 原因 |
|--------|------|------|
| P0 | B1 + B2（结构化错误 + 8 种分类）| AI 调用方最痛，误判成 bug 后果重 |
| P0 | A1（启动横幅去噪）| 影响每一次调用的输出纯净度 |
| P1 | B4（失败总结一行）| 长日志找不到结论，AI 抓不准 |
| P1 | A2（场景速查 --help）| 降低 AI 学习成本 |
| P2 | B3 / B5 | 体验优化 |
| P2 | A3（陷阱段）| 文档完善 |

### 拆批建议

- **Batch 1**（P0 必做）：A1 + B1 + B2 + B4 + B5 — 一次性把"日志噪音 + 错误体验"做到能用
- **Batch 2**（P1 可选）：A2 + A3 — 文档优化，独立可做

### 下游 skill 等 wf 优化完再做

skill 写得很薄：
- 触发：用户说"抓页面/读文章/扒数据" 时启动
- 模式决策：URL → 直接 wf；含图 → 提示 `-o`；批量 → 提示 `wf batch`
- 一切细节：让 AI 自己 `wf --help` 查 或 看报错 `建议:` 字段路由

## 验收标准（实施时）

- `wf https://example.com --stdout 2>&1` 默认无启动横幅噪音
- `wf not-a-url` 输出结构化错误（无 traceback），exit code 非 0
- `wf https://expired.badssl.com/` 重试失败后末尾有总结行
- `wf --help` 含"AI agent 场景速查"段
- 单元测试覆盖 8 种错误分类
- 现有调用方（CHANGELOG / API）行为不变（仅输出格式优化）

## Out-of-Scope

- 不改 CLI 入口参数（保持兼容）
- 不改 Python API 返回值
- 不重构 fetch_html_with_retry / generic_v2 等内部函数
- 不改 routing.yaml schema

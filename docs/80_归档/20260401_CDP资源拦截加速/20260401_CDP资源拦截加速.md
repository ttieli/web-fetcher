# CDP 资源拦截加速（--fast 模式）

> 创建时间：2026-04-01

## 原始需求

fetcher-mcp 通过拦截 image/css/font/media 资源，同一篇公众号文章从 43s 降到 8s（快 5.5x）。用户希望将此优化引入 wf，但有多个设计不确定性需要评估。

## 需要评估的关键问题

### 1. 图片信息丢失
很多公众号/小红书文章的图片本身包含关键信息（图表、截图、公式）。拦截图片后 Markdown 中不会有图片链接，内容不完整。
- 方案 A：拦截图片下载但保留 img src（只跳过实际下载，HTML 中 src 属性仍在）
- 方案 B：拦截所有图片请求，Markdown 中无图片
- 方案 C：只拦截非内容图片（广告、装饰、icon），保留内容图片

### 2. 自动升级/降级策略
- 方案 A：由调用方显式选择模式（简单，无魔法）
- 方案 B：先 fast，检测到"图片占比高"时自动重抓 full 版本
- 方案 C：默认 fast，输出中标注"图片已跳过"，让调用方决定是否重抓

### 3. AI Agent 调用场景
wf 大部分被 skill 调用。AI agent 需要：
- 清晰的 help 文本说明何时用 fast vs full
- 机器可读的输出标记（如 `<!-- mode: fast, images_skipped: true -->`）
- 考虑场景：分析文章内容→fast 够了；保存完整文章→需要 full

### 4. 命名冲突
现有 `wf fast` 命令已存在，含义是"跳过 JS 渲染"（`--render never`），与新的"资源拦截加速"是不同概念。需要新命名。

### 5. 实现层选择
- CDP 层（pychrome）：`Network.setRequestInterception` — 只对 CDP 模式有效
- Playwright 层：`context.route()` — 只对 render 模式有效
- 两层都加 vs 只加 CDP 层

### 6. 与 --download-assets 的关系
- fast + download-assets = 矛盾？（拦截了图片又要下载？）
- 需要明确互斥规则或优先级

## 细化记录

### 源码分析发现

1. **现有 `wf fast` 命令**（cli.py:951）含义是 `--render never --timeout 30`，与新需求不同
2. **CDPFetcher.fetch()** 中 `tab.Network.enable()` 已调用，可在此基础上加 `setRequestInterception`
3. **download_assets**（core.py:5350）对微信/小红书默认自动启用，fast 模式需要覆盖此行为
4. **图片链接保留**：CDP 拦截的是实际 HTTP 请求，HTML 中的 `<img src>` 属性不受影响。这意味着 Markdown 中仍会有 `![](url)` 链接，只是图片不会被下载/缓存

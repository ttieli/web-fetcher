## 一、关键发现（必须优先关注）

### 发现 1: `hint_strategy` 形同虚设（Bug）

`extractors.py:run_competition()` 接收了 `hint_strategy` 参数但**完全未使用**：

```python
# extractors.py L276-317
def run_competition(html, url, hint_strategy=None):
    strategies = [extract_trafilatura, extract_readability, extract_next_data, extract_json_ld]
    results = []
    for fn in strategies:          # ← hint_strategy 未被用来跳过或优先排序
        result = fn(html, url)
        ...
```

这意味着即使域名记忆中已有高置信度的最佳策略，**每个 URL 仍然跑完全部 4 个策略**。修复后同域名 URL 解析可提速 ~4x。

### 发现 2: 站点采集强制 V1 解析器

`core.py:4846` 硬编码：
```python
parser_func = generic_to_markdown  # V1 legacy 解析器
```

**完全跳过 V2 竞赛引擎、站点模板、域名记忆**。这是 site 模式解析质量低于单页模式的根本原因。

### 发现 3: DomainMemory 每次重新实例化

`engine_v2.py:94`：
```python
memory = DomainMemory()  # 每次调用 generic_v2 都新建实例，读一次磁盘
```

batch 模式下 100 个 URL = 100 次磁盘读 + N 次写，且**同批次内的记忆积累无法跨 URL 利用**。

## 四、各优化点详细分析

### 4.1 批量采集 (wf batch)

#### 并发能力

**现状**：严格顺序执行，每个 URL 独立调用 `core.main()`，重复初始化路由引擎、模板解析器、域名记忆。

**推荐方案**：`ThreadPoolExecutor` + 按域名分桶
- 同域名串行 + 请求间隔（避免被封）
- 不同域名并发（最大化 I/O 利用）
- CDP/Selenium 连接池（2-3 个 session，semaphore 控制）

**预期**：10 个不同域名 URL 从 ~30s 降至 ~6-8s

#### 域名记忆复用

**现状**：每个 URL 都完整跑 4 策略竞赛（~500ms），`hint_strategy` 参数接收但未使用。

**推荐方案**（3 级）：
1. Level 1：DomainMemory 单例 + 延迟写盘
2. Level 2：高置信度域名只跑推荐策略（从 4 策略降为 1 策略）
3. Level 3：batch 开始前按域名预查记忆，规划资源调度

#### 错误处理与断点续传

**现状**：无进度持久化，进程中断后从头再来。

**推荐方案**：
- `.wf_batch_progress.json` 进度文件
- 启动时检测已有进度，自动续传
- 结束时输出汇总统计（成功/失败/跳过/耗时）
- `--retry-failed` 参数重试失败 URL

#### 输入格式

**现状**：仅纯文本 URL 列表。

**推荐方案**（渐进增强）：
1. 注释支持（`#` 开头跳过）— 3 行代码
2. JSON/CSV 支持（每 URL 可指定 fetch_mode/engine）
3. 分组模式（按项目/域名组织，组级参数）

#### 输出管理

**现状**：平铺在同一目录，无 URL-文件映射，无去重。

**推荐方案**：
- 生成 `_index.json` 索引文件
- URL 去重（`normalize_url()`）
- 可选按域名分子目录 `--group-by-domain`
- 增量模式 `--skip-existing`

---

### 4.2 站点采集 (wf site)

#### 爬取策略

**现状**：BFS 广度优先，所有链接一视同仁，每页最多入队 50 条（按字母序截断）。`category_first` 策略仅限政府站点。

**推荐方案**：
1. 优先级队列替代 deque（按 URL 评分排序）
2. 通用分类策略（基于 `<nav>`/`<header>` 自动发现）
3. 自适应深度控制（低质量分支自动剪枝）
4. sitemap + BFS 混合（sitemap URL 作为高优先种子注入队列）

#### 解析质量（最关键）

**现状**：硬编码 V1 `generic_to_markdown`，完全跳过 V2 竞赛引擎和站点模板。

**推荐方案**：分层解析
1. 检查站点模板是否匹配 → 命中直接使用
2. 首页走完整 V2 竞赛 → 确定最佳 extractor
3. 后续页面用域名记忆直接使用 winner → 跳过竞赛

新增 `--engine v1/v2/auto` 参数，默认 `auto`。

#### 输出格式

**现状**：所有页面聚合为单一 Markdown（100 页 = 500KB+ 单文件）。

**推荐方案**：新增 `--output-mode single|multi|both`
```
multi 模式:
  output_dir/
    _index.md          # 索引
    _index.json         # 结构化元数据
    001_page_title.md   # 独立页面
    002_another.md
```

#### 增量爬取

**现状**：完全不支持，每次全量 BFS。sitemap 的 `lastmod` 字段被解析但仅用于排序。

**推荐方案**：
- `~/.config/webfetcher/crawl_state/` 持久化已爬取 URL + content_hash
- `--incremental` 模式：仅爬取新增或变更的页面
- 与 sitemap lastmod 联动

### 4.3 共享架构

#### 统一 PageProcessor

**核心洞察**：batch 和 site 的区别仅在 **URL 来源**（文件 vs BFS 发现）和 **输出格式**（独立文件 vs 聚合），中间的处理管道完全可以统一：

```
URL 来源(不同) → 统一调度层(共享) → 单页处理管道(共享) → 输出组装(不同)
```

建议抽取 `PageProcessor` 类：
```python
class PageProcessor:
    def __init__(self, engine='auto', memory=None):
        self.memory = memory or DomainMemory()

    def process(self, url, html) -> (title, markdown, metadata):
        # 路由 → 抓取 → 模板/V2/V1 → 输出
```

#### 统一调度层

```python
class MultiURLScheduler:
    # 并发控制（同域名礼貌策略 + 跨域名并行）
    # 域名记忆预热和批量利用
    # 进度持久化和断点续传
    # 统一错误处理和重试
```

#### 第三种模式：频道采集

介于 batch 和 site 之间：
- **输入**：RSS 源 / 列表页 URL
- **发现**：自动提取文章链接（非 BFS 全站）
- **输出**：按频道分组的独立文件

典型场景：微信公众号历史、新闻频道分页、RSS 订阅。
